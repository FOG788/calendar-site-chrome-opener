# 実装失敗の分析メモ（2026-05-12）

## 1) なぜ「最初に」最適な提案ができなかったか

### 結論
最初の提案では、要件の「**変更してよい範囲**」を十分に固定せず、
「機能を柔軟化する実装（内部ロジック変更）」まで踏み込んでしまったためです。

### 具体的な見落とし
1. **要求の中心は“タイミング変更のみ”だった**
   - ユーザー意図は「音量指定方式はそのまま」「実行タイミングだけ可変化」だった。
   - しかし初回対応では、`applyVolumeWhenReady` の実行モデルまで変更し、結果として不具合要因を増やした。

2. **互換性より拡張性を優先しすぎた**
   - 設定項目追加自体は正しいが、同時に注入スクリプト内の遅延制御方式を変えたことで、
     実サイト差異（プレイヤー準備タイミング等）への耐性が落ちる可能性を作った。

3. **“最小差分原則”の適用不足**
   - 本件は既存の成功している音量適用ロジックに対して、
     「いつ呼ぶか」だけを外側で調整すればよいタスクだった。
   - それなのに「どう適用するか」まで触ってしまった。

### 再発防止ルール
- 仕様変更時は先に以下を明文化してから着手する。
  - **不変条件（変えてはいけないもの）**
  - **可変条件（今回変えるもの）**
- 既存で動作実績がある処理は、まず「呼び出し側の制御変更」で解けないか検討する。
- “拡張したい”実装があっても、まずは最小差分で1回通す。

## 2) このリポジトリで確認できる実装失敗の棚卸し

以下は Git 履歴・README・AI ノートから読み取れる失敗/再発ポイントです。

## A. Service Worker 構文エラー（起動不能）
- 症状: `Service worker registration failed. Status code: 15` / `missing ) after argument list`
- 影響: 拡張機能の主要機能が全停止
- 兆候: README にトラブルシューティングが追加されている
- 根本原因:
  - 手修正時の構文破壊
  - リロード時のキャッシュ/古い SW 反映遅れ
- 予防策:
  - 変更後に必ず `node --check service_worker.js`
  - 大きな関数変更時は小分けコミット

## B. 音量制御とループ制御の責務混在
- 症状: ユーザーが手動で変えた音量が効かない/戻る
- 影響: UX 悪化、機能への不信
- 兆候: `AI_NOTES.md` に「ループ側で音量再適用するな」と明記
- 根本原因:
  - ループの定期処理に音量適用を混ぜる設計
- 予防策:
  - Loop と Volume の処理経路を完全分離
  - Volume は起動直後の有限回リトライのみ

## C. 今回の回帰：タイミング変更要件なのに適用方式まで変更
- 症状: 「音量指定が機能しなくなった」という回帰報告
- 影響: 既存ユーザーの運用停止
- 根本原因:
  - 要件解釈の過剰一般化（柔軟化のために内部方式まで変更）
- 是正:
  - 実行タイミングのみ外側でスケジュールし、適用本体は従来方式に戻す

## D. 設定キー変更時の移行配慮不足リスク
- 症状: 既存設定の意味が変わる/初期値で上書きされる懸念
- 影響: 期待しない動作、設定再入力コスト
- 根本原因:
  - 旧キー廃止時に移行方針が曖昧
- 予防策:
  - 旧キー→新キーの変換を `normalizeSettings` で明示
  - リリースノートに移行内容を明記

## E. テスト運用の弱さ（手動確認依存）
- 症状: 修正後の回帰を検出しにくい
- 影響: 同種バグ再発
- 根本原因:
  - 自動テスト不在
  - 最低限の静的チェック手順がルーチン化されていない
- 予防策:
  - 最低限の「変更後チェックリスト」を固定化
    - `node --check service_worker.js`
    - 設定保存→再読込→反映確認
    - YouTube等で音量適用3回タイミング確認

## 3) 今後の実装ガイド（短縮版）

1. **仕様ロック**
   - 「今回変えないもの」を1行で先に合意する。

2. **最小差分で先に通す**
   - まず呼び出しタイミングのみ変更。
   - 内部アルゴリズムは後続PRで分離。

3. **責務分離を守る**
   - Loop: ループ状態のみ。
   - Volume: 有限回の初期適用のみ。

4. **SW構文チェックを必須化**
   - `node --check service_worker.js` をコミット前必須にする。

5. **回帰観点をドキュメント化**
   - 「今回壊した点」を次回PRテンプレに残す。

## 4) 今回の学び（要約）

- うまくいくコードは「賢い変更」より「壊さない変更」。
- ユーザー要求が明確なときは、拡張よりも境界厳守を優先する。
- このリポジトリでは特に、`service_worker.js` の小さな変化が全機能停止に直結するため、
  変更半径を最小化するのが最重要。
